<objective>
Partially close the HOST-04 (SC4) gap `01-VERIFICATION.md` found: "`pod0-nostr-host`'s `NostrPublisher` still constructs and owns its own `tokio::runtime::Runtime` (`rust/crates/pod0-nostr-host/src/publisher.rs:38`) rather than accepting an externally-threaded `Handle`... If `pod0-nostr-host` were linked into `pod0-cli` today, the single-shared-runtime invariant would be violated immediately."

This plan fixes the concretely-fixable half of that finding: it gives `NostrPublisher` an additive, `Handle`-based construction path (mirroring the exact pattern `01-02-PLAN.md` already established for `pod0-portable-media`'s `MediaLoader::new_with_handle`), so that if/when `pod0-nostr-host` is wired into a shared process, it will no longer independently own a second runtime.

**What this plan does NOT do, and why — flagged explicitly, not silently narrowed:** `01-VERIFICATION.md`'s SC4 finding also states "no process or crate in the workspace links all six host crates together" — `pod0-cli` does not depend on `pod0-nostr-host`, `pod0-system-hosts`, or `pod0-tts-host` today. Actually wiring `pod0-nostr-host` into `pod0-cli`'s process (to produce a real, testable "all six crates share one runtime" proof) requires routing Nostr-publication commands through `pod0-cli`'s `HostExecutor`, which requires a new `HostRequest`/`HostObservation` variant (or equivalent contract surface) in `pod0-application`/`pod0-facade` — those files are explicitly frozen for this gap-closure work (see `01-04-PLAN.md`'s scope boundary). That wiring is real, non-trivial product work, not a "too hard, skip it" judgment call: it is a genuine dependency conflict against this plan's file boundary. **Recommendation for the user/roadmapper:** either schedule a follow-up phase (once facade/storage contract work is in scope) to actually wire `pod0-nostr-host`/`pod0-system-hosts`/`pod0-tts-host` into `pod0-cli` and prove SC4 end-to-end, or reword ROADMAP.md Phase 1's Success Criterion 4 to reflect that only the crates currently linked into a process (`pod0-live-hosts`, `pod0-portable-media`, via `pod0-cli`) are provably sharing one runtime today, with `pod0-nostr-host` now Handle-ready (this plan) but not yet linked.

Purpose: removes the one concrete, self-documented regression risk (an owned second runtime that would deadlock or double up on I/O drivers the moment `pod0-nostr-host` is ever linked into a shared process) without requiring any facade/storage contract change.
Output: `NostrPublisher::new_with_handle`, additive, with a test proving cross-thread `Handle::block_on` correctness for this crate's own actual `publish_to_relay` I/O path (not just a toy example).
