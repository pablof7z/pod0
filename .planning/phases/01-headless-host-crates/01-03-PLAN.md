<objective>
`pod0-cli::HostExecutor` currently auto-denies every agent approval (`host.rs:101`, `AgentApprovalDecision::Deny` unconditionally) and unconditionally fails every capability execution (`host.rs:104-108`, blanket `unsupported_observation`) — the opposite of native `AgentApprovalCoordinator`, whose own doc comment states Pod0 "does not interrupt the owner to authorize the owner's own agent" and always returns `.approve`. This is the last gap standing between the headless host and validating the real `pod0-application` approval/capability state machine outside the iOS simulator (HOST-05).

Full capability parity is architecturally impossible in this phase: native's `LiveCoreAgentCapabilityExecutor` depends on `AudioEngine`, `PlaybackState`, and `ElevenLabsTTSClient`, none of which have a headless equivalent (this matches REQUIREMENTS.md's own out-of-scope line: moving `AVAudioSession`/TTS ownership into Rust is an explicit non-goal). The one capability action that is genuinely, fully replicable headlessly — `AgentToolAction::Search{tool: SearchPodcastDirectory, ..}` — is pure HTTP and `pod0-cli/src/host/search.rs` already implements the identical iTunes search logic, currently wired only to a CLI `search` subcommand. This plan flips the approval decision, wires that one capability end to end, and proves the whole chain with a real headless integration test — closing HOST-05 to the depth the requirement actually asks for (state-machine proof, not full capability coverage) rather than the depth a literal reading of "capability-execution parity" might overreach into.

Purpose: prove headlessly that a tool-call turn can be approved and executed for real, not silently denied or blanket-failed.
Output: `AgentApprovalDecision::Approve` by default; a new `capability.rs` module wiring `searchPodcastDirectory` to real HTTP search with a specific `Failed` message for every other action; a passing integration test exercising the full loop.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Model-proposed tool call -> headless capability execution | A durable-core-approved tool call now triggers a real outbound HTTP request (iTunes search) with no human in the loop, matching native's existing "agent approves itself" design |
| `AgentCapabilityOutcome::Succeeded{bounded_result}` -> durable core observation acceptance | The search JSON payload must independently satisfy the core's own byte bound or the observation is rejected |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-------------------|
| T-03-01 | Denial of Service / Elevation of Privilege | `capability::execute`'s `Search` case issuing a real HTTP request headlessly on every approved tool call | medium | mitigate | Reuses `search.rs`'s existing `MAX_SEARCH_RESULTS`/`MAX_SEARCH_RESPONSE_BYTES` clamps at the HTTP layer, plus this plan's new `MAX_AGENT_MESSAGE_BYTES` clamp at the durable-core-observation layer (Task 2) — two independent bounds, neither bypassed by the new wiring. |
| T-03-02 | Repudiation | Approval auto-approves every proposal unconditionally (`AgentApprovalDecision::Approve`, no conditional logic) | low | accept | Matches native `AgentApprovalCoordinator`'s documented, already-shipped behavior ("Pod0 does not interrupt the owner to authorize the owner's own agent") — this plan brings the headless host into parity with an existing, accepted native design decision, not a new risk this phase introduces. |
| T-03-03 | Elevation of Privilege | Every non-search `AgentToolAction` now reaches `capability::execute`'s catch-all instead of the old blanket rejection | low | accept | The catch-all still returns `Failed`, never `Succeeded` or a side-effecting outcome — behaviorally equivalent to the prior blanket-`Unsupported` response for every action except `SearchPodcastDirectory`, which is the one intentionally, narrowly enabled case. |
