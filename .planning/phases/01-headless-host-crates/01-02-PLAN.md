<objective>
Two runtime-collision and HTTP-duplication bugs already live in the working tree (not hypothetical, verified by direct inspection this session): `pod0-cli::HostExecutor::new` (`host.rs:45`) and `pod0-portable-media`'s `MediaLoader::from_client_builder` (`source.rs:95`) each independently call `tokio::runtime::Builder::new_current_thread()...build()`, and both runtimes coexist in the same `pod0-cli` process whenever a playback request is dispatched (`HostPlayer::new` in `host/playback.rs` calls `MediaLoader::new` on the host-pump worker thread, which already holds a `HostExecutor` with its own runtime). Separately, `HostExecutor.client` (a `reqwest::blocking::Client`) and `LiveHosts`'s internal async `reqwest::Client` are two independently-pooled HTTP clients live in the same process; `pod0-live-hosts::LiveHosts` already exposes `http_get`/`openai_chat`/`ollama_chat` as the async equivalents needed to delete the blocking client entirely.

This plan consolidates both down to one runtime and one pooled client per process (HOST-04, HOST-03), and as a direct consequence of migrating `agent_http.rs` onto `LiveHosts::openai_chat`/`ollama_chat` (which already parse tool calls fully), fixes a gap not previously called out anywhere: `agent_http.rs::completed()` hardcodes `proposed_tool_call: None` unconditionally today, meaning no headless test can exercise a tool-call-producing turn at all — which is exactly the case Plan 3's approval-parity fix (HOST-05) needs to be provable. This plan also adds the D-02 tracing instrumentation while the same call sites are already being touched.

Purpose: eliminate the two duplicate-resource bugs HOST-03/HOST-04 name, and unblock HOST-05's approval flow from being reachable in headless tests as a necessary side effect.
Output: one runtime `Handle` shared by every host adapter in the process; one pooled, timeout-bound async HTTP client used by every provider/feed/search call; tool-call proposals surfaced instead of dropped; tracing spans on every outbound HTTP call.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| pod0-cli process <-> external HTTP providers (OpenAI-compatible, Ollama, iTunes) | Now flows through one pooled, timeout-bound `LiveHosts` client instead of two independently-configured clients |
| pod0-live-hosts/pod0-tts-host tracing spans <-> log sink | New span output could leak secrets if instrumentation is done carelessly |
| Provider HTTP response -> `AgentModelCompleted.proposed_tool_call` | A tool-call proposal now reaches the durable core's approval gate instead of being rejected at the transport layer |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-------------------|
| T-02-01 | Information Disclosure | `#[tracing::instrument]` spans in `pod0-live-hosts`/`pod0-tts-host` | high | mitigate | `skip(self, request, cancellation)` on every instrumented method plus a post-hoc grep for `body`/`bearer_token`/`api_key`/`Authorization` in span field names (Task 3's acceptance criteria); reuse `RedactedUrl` for any URL field, matching the existing `ProviderEndpoint`/`RedirectEvidence` Debug-redaction pattern already in `pod0-live-hosts`. |
| T-02-02 | Tampering | `fetch_feed`/`fetch_library`/`search::search`'s response-size and conditional-GET bounds during the blocking-to-async client migration | medium | mitigate | `HttpLimits{maximum_body_bytes}` is threaded from the exact same `maximum_response_bytes`/`MAX_SEARCH_RESPONSE_BYTES` constants the old blocking-client code already enforced — Task 2's action explicitly preserves these bounds rather than dropping them during the migration. |
| T-02-03 | Spoofing / Elevation of Privilege | A provider response proposing a tool call the model was never advertised (`agent_http.rs`'s removed `contains_tool_call` guard) | medium | accept | Validation moves to its correct architectural layer — `pod0-application::agent_provider_output::AgentProviderOutputError::UnsupportedTool` already validates a proposed tool name against the durable core's own `AgentToolName` catalog; duplicating that check in the Rust host adapter was redundant defense in the wrong tier per RESEARCH.md's Architectural Responsibility Map. Plan 3's approval-parity fix additionally means any accepted proposal still requires an explicit `PresentAgentApproval` round-trip before any capability executes. |
| T-02-04 | Denial of Service | Oversized `arguments_json` on a newly-surfaced `proposed_tool_call` | low | accept | `pod0-application::contract_state_agent_validation::tool_call_is_bounded` already enforces `MAX_AGENT_TOOL_ARGUMENTS_BYTES`/`MAX_AGENT_TOOL_NAME_BYTES`/`MAX_AGENT_TOOL_CALL_ID_BYTES` on every `AgentModelCompleted` observation the durable core accepts — pre-existing control, unaffected by this migration. |
| T-02-SC | Tampering | New `tracing`/`tracing-subscriber` workspace dependencies | low | accept | Both verdict "OK / Approved" in 01-RESEARCH.md's Package Legitimacy Audit (maintained by the `tokio-rs` GitHub org, same maintainers as the already-pinned `tokio`); no blocking checkpoint required per the package-legitimacy gate rule, which only requires one for `[ASSUMED]`/`[SUS]` verdicts. |
